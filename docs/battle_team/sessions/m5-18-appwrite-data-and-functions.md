## Session log
Built (2026-11-05), stacked on M5.17 (hawkbee #54, not merged yet):
- **`battle_backend`**, a new package (public repository `hawkbee1/battle_backend`, merge commits only, submodule, in the root `workspace:` and melos `format` lists): the logic the functions wrap (stack decision 8), so each function stays a thin adapter.
  - `Wars`:
    - An admin creates a war, plans its battles and starts the next one. Its teams are the war's sections balanced by power, each guild together (SOC-20, decision 103).
    - A player joins a war with a new section: the war's starting money and a commander. During a battle, the section joins the weakest team (SOC-02, SOC-30).
    - `end` carries over a battle its host ended: each section keeps its `KeptSection`, each guild earns the XP its sections earned (SOC-47), and the war goes on or ends (SOC-17).
  - `Guilds`: guild requests between battles, with `GuildRules`.
  - `ApiKeys`: one key per account, generated by the server and shown once; stored as its SHA-256; revoked by its user or an admin; `accountOf` refuses a revoked key from the next call on.
  - `Rows` (port) with `MemoryRows` and `AppwriteRows`; `Admins` with `AppwriteAdmins` (the Appwrite label `admin`, stack decision 6); `serve`, `answer` and the field readers of the function kit.
  - The rule refusals come out as `Refused` codes in snake case with an HTTP status.
- **`hawkbee_schema`**: the row models `WarRow`, `BattleRow` (with `BattleStatus` and `BattleResult`), `SectionRow` (with `KeptSection` and `KeptUnit`), `GuildRow` and `ApiKeyRow`, and the IDs of the tables, the functions and the admin label.
- **hawkbee `backend/`**:
  - Tables `wars`, `battles`, `sections`, `guilds`, `purchases` and `api_keys`; lists and maps are JSON text columns.
  - Functions `create_war` (create, join), `create_battle` (plan, start), `end_battle` (on the update of a battle's row), `guild_requests` and `api_keys` (create, revoke), each a `respond` over `battle_backend`.
  - `daily_stats` now runs on a daily schedule. It runs every battle running and every ended battle whose statistics are not final yet, then marks those final. A body naming a battle still runs that one.
  - `tool/vendor_packages.dart` also vendors `economy.yaml`, which lives in `plan/milestones/`.

Checks: analyze `--fatal-infos` and format clean; tests pass with 100 % coverage, optimization off: `battle_backend` 29 (and the opt-in Appwrite suite, skipped), `hawkbee_schema` 8, `create_war` 4, `create_battle` 3, `end_battle` 3, `guild_requests` 3, `api_keys` 4, `daily_stats` 15.

Acceptance criteria:
- A war created, a battle set up, ended and carried over to the next: on tables in memory (`battle_backend/test/src/wars_test.dart`); on the local instance, `test/live/appwrite_backend_test.dart`, opt-in, **not run**.
- A revoked key is refused at once: in memory (`api_keys_test.dart`); on the local instance, the same opt-in suite, **not run**.

Not run on the local instance, and the 30-second synchronous limit not measured. From the container, `appwrite-traefik` does not resolve. `host.docker.internal` reaches an Appwrite 1.9.0 when the request says `Host: localhost`, but it has no `hawkbee` project, and the container has no API key for it. Nothing was pushed.

Choices:
- The function logic is a package, `battle_backend`, rather than code copied into five functions. The vendor tool copies it into each function with its workspace dependencies.
- No `commanders` table: an account's commanders are the commanders of its sections, one per war. No `medal_definitions` table: the definitions are the plan's `medals.yaml`, vendored into the functions as `plan_data`; the results are M5.17's `medals` table.
- Admins are the accounts with the Appwrite label `admin`, checked in the functions.
- `create_war` also takes the joining of a war. A new section has the war's starting money and its commander, `<section>-commander`; its ID is a hash of the war and the account.
- The host reports a battle's end by updating its row: status `ended`, the winner and a `BattleResult`, which holds what each section keeps and the XP its units earned. That update triggers `end_battle`. The host writes it from M5.19.
- A newcomer joining during a battle goes to the weakest team. A tie is drawn with a random of the battle's seed and its number of sections, so a join made again draws the same.
- The function client defaults to `http://localhost/v1` outside Appwrite. Appwrite always sets the endpoint and the project of an execution.
